# 课堂演示版调整说明：系统自治 · 数据自造 · 零外部集成

> 版本：v1.0　编制日期：2026-10-20
> 适用前提：**课堂演示用**，无供应商、无采购部门、无人事系统、无真实支付网关、无物流
> 结论：**所有业务数据都在本系统内产生**，凡"外部来源"改为"管理端直接录入"

---

## 0. 一句话原则

> **凡是原来"等别人送数据进来"的地方，一律改成"经理在界面上自己填进去"。**
> 系统不假装有上游，而是把上游的动作收敛成一个表单。

这不仅是简化，对课堂演示其实是**加分项**：整条链路可复现、可重复演示、不依赖网络与环境。

---

## 1. 哪些能简化、哪些不能（先划这条线）

这是本文档最重要的一节。简化错了地方，系统就只剩壳子；该简化的地方硬做，白花时间。

| 环节 | 处理 | 理由 |
|---|---|---|
| 补货 / 入库 | ✅ **简化为后台直接录入** | 上游是采购与供应商，课堂上无法也不必要模拟 |
| 报损 / 盘点 | ✅ 简化为后台录入 | 无仓管部门，经理一人完成 |
| 商品 / 会员 / 员工建档 | ✅ 简化为后台录入 | 无主数据系统、无人事系统 |
| 支付 | ✅ **模拟渠道 + 系统内自触发回调** | 无商户资质，且演示需要可控的成功/失败 |
| 短信验证码 | ✅ 固定验证码或免验证 | 无短信服务商 |
| 门店 | ✅ 单店，参数页可改 | 无连锁总部 |
| **库存扣减一致性** | ❌ **不可简化** | 预占/释放/实扣是"设计含量"所在，简化了答辩没得讲 |
| **支付幂等** | ❌ **不可简化** | 重复回调不重复扣款，是最能体现工程能力的点 |
| **订单状态机** | ❌ **不可简化** | 状态合法性校验是系统严谨性的直接证据 |
| **优惠分摊** | ❌ **不可简化** | 不分摊到行，退货金额必然错——这恰恰是最好的演示点 |

**一句话**：**入口可以伪造，账不能算错。** 数据从哪来不重要，数据进系统之后怎么流转才重要。

## 3. 补货功能详细设计（重点）

用户点名的地方，写细一点。**核心思想：不做出入库单据流，做一个"补货表单"。**

### 3.1 三个入口（按演示顺手程度排序）

**入口 1：库存预警列表的"快捷补货"（最出彩，演示就用这个）**

```
管理端 → 库存管理 → 库存预警
┌──────────────────────────────────────────────────────────────┐
│ SKU         商品名        当前库存  安全库存  状态    操作      │
│ SKU10023    鲜牛奶 1L        3        20      ⚠ 不足  [补货]  │
│ SKU10088    Member's 抽纸    8        30      ⚠ 不足  [补货]  │
└──────────────────────────────────────────────────────────────┘
        ↓ 点击 [补货]
┌─────────────────────────────────────┐
│ 补货：鲜牛奶 1L（SKU10023）          │
│ 当前库存：3      单位：瓶            │
│ 补货数量：[ 100        ]             │
│ 进货单价：[ 6.80  ] 元（默认上次进价）│
│ 备注：   [ 供应商直送          ]     │
│                    [取消] [确认补货] │
└─────────────────────────────────────┘
        ↓ 确认
提示：补货成功，当前库存 103（+100）
```

**入口 2：批量补货** —— 列表勾选多行 → 顶部"批量补货" → 表格内逐行填数量 → 一次提交。用于演示"一次给 10 个商品补货"。

**入口 3：补货记录** —— 单据列表，可查明细（谁、何时、补了什么、补多少、单价、金额）。用于演示"库存有据可查"。

### 3.2 表结构（沿用 `stock_bill`，去掉供应商与采购单关联）

```sql
-- 库存单据（补货 / 报损 / 盘点）
stock_bill (
  id            bigint primary key,
  bill_no       varchar(32)  unique,      -- IN20261020001 / LS... / CK...
  type          varchar(16),              -- INBOUND / LOSS / CHECK
  source        varchar(16),              -- MANUAL（本系统录入，唯一值）
  store_id      bigint,
  operator_id   bigint,                   -- 谁录的
  total_qty     int,
  total_amount  bigint,                   -- 分
  remark        varchar(255),
  status        varchar(16),              -- CONFIRMED（提交即生效，无审批）
  created_at    datetime
)

stock_bill_item (
  id          bigint primary key,
  bill_id     bigint,
  sku_id      bigint,
  qty         int,
  cost_price  bigint,                     -- 分，用于毛利与成本快照
  amount      bigint                      -- qty * cost_price
)
```

> **取消了什么**：`supplier`、`purchase_order`、`purchase_order_item`、审批状态、到货确认。四张表和两个流程全部不存在。

### 3.3 接口（4 个，够用）

| 接口 | 说明 |
|---|---|
| `GET /stock/warning/list` | 预警列表（`available < safety_stock`），带"上次进价" |
| `POST /stock/replenish` | 单条补货：`{skuId, qty, costPrice?, remark, requestId}` |
| `POST /stock/replenish/batch` | 批量补货：`{items:[{skuId,qty,costPrice}], remark, requestId}` |
| `GET /stock/bill/page` | 单据分页（按类型/时间/操作人筛） |

### 3.4 业务规则（写进代码注释，也是答辩要讲的）

1. `qty > 0`，单次上限 9999（防手抖输错）；
2. `costPrice` 缺省取该 SKU 最近一次进价，仍无则取 `sku.cost`；
3. **提交即生效**，不设审批（课堂上没有第二个人来批）；
4. 事务内完成三件事：写单据+明细 → `on_hand += qty, available += qty, version += 1` → 写库存流水（记录 `before` / `after`）；
5. 若本次进价与 `sku.cost` 不同，**更新 `sku.cost` 并留一条成本变更记录**（毛利才算得对）；
6. `requestId` 幂等，防连点；
7. 权限 `stock:replenish`，仅经理与管理员。

### 3.5 演示台词（30 秒）

> "经理发现鲜牛奶只剩 3 瓶，低于安全库存 20。点补货，填 100，确认——库存立刻变成 103，POS 端马上可以卖。这一笔补货生成了单据 IN20261020001，库存流水里能看到 '3 → 103'，操作人是张三。**库存的每一次变化都有据可查，不存在直接改数字的情况。**"

这句话把"简化了流程"讲成了"保留了可追溯性"，是加分点。

### 3.6 报损与盘点（同一套思路）

- **报损**：选 SKU + 数量 + 原因（过期/破损/试吃）→ 提交 → `on_hand -= qty, available -= qty` → 写流水。同样无审批。
- **盘点**：创建盘点单（选范围）→ 列表内直接填实盘数（表格可编辑）→ 提交 → 系统算差异 → 经理确认 → 生成调整单 → 更新账面并写流水。
  - **不做 Excel 导入**：课堂上录 5 个商品即可演示。
  - 演示时故意造一个差异（账面 100，实盘 95），展示"差异 5 瓶，金额 34 元，需说明原因"。

## 4. 模拟支付的设计（第二个关键点）

### 4.1 设计

```
POS 点击"微信支付"
   → POST /pay/create  →  返回 payNo + 模拟二维码内容
   → 前端显示"等待扫码…"遮罩（2 秒）
   → 前端自动调 POST /pay/mock-callback {payNo, result: SUCCESS}
   → 走后端真实回调逻辑（唯一索引 + 状态机校验）
   → 订单置为已支付 → 触发库存实扣、积分、券核销 → 出小票
```

**关键：`/pay/mock-callback` 只是"制造一个回调"，回调之后的处理必须走真实逻辑。** 这样重复调用它就能演示幂等——**故意点两次"模拟成功"，库存只扣一次、金额只加一次**，这是最好的幂等演示。

### 4.2 演示面板（建议做，10 分钟工作量，效果很好）

在 POS 支付弹窗加一个不显眼的调试区（`demo` 环境才显示）：

| 选项 | 用途 |
|---|---|
| 支付结果：成功 / 失败 / 超时 | 演示异常流：失败后重试、超时后订单保持待支付 |
| 回调次数：1 / 2 / 5 | 演示幂等（点 5 次只生效 1 次） |
| 延迟：0s / 2s / 5s | 演示"支付中"状态与取消 |

### 4.3 保留可替换性（答辩要讲）

`PayChannel` 接口不变，四个实现：`CashChannel`、`MockWechatChannel`、`MockAlipayChannel`、`StoredValueChannel`。
答辩时说：**"接真实微信支付，只需新增一个 `WechatPayChannel` 实现类，业务代码零改动。"** 这把"没接真实支付"从缺点讲成了架构优势。

## 5. 演示数据与一键重置（课堂演示的命门）

课堂上最怕两种情况：**报表全是 0（没有历史数据）**、**演示过一次后数据脏了**。

### 5.1 三份脚本

| 脚本 | 内容 | 时机 |
|---|---|---|
| `V1__init.sql` | 建表（Flyway 管） | 部署时 |
| `demo-base.sql` | 基础数据：1 门店、8 员工、3 角色、8 分类、**60 个 SKU**（含 8 个称重生鲜）、3 个会员（1 正常 / 1 储值充足 / 1 已过期）、2 个活动、5 张券 | 初始化 |
| `demo-orders.sql` | **300 笔历史订单**，跨 30 天，随机商品与支付方式，状态已支付，用于报表出曲线 | 演示前 |

### 5.2 两个演示工具接口（仅 `demo` profile 开放）

| 接口 | 作用 |
|---|---|
| `POST /demo/seed-orders?days=30&count=300` | 一键生成历史订单，报表立刻有数据 |
| `POST /demo/reset` | 清空业务表（订单/支付/班次/库存流水），保留商品会员等基础数据，回到演示起点 |

> **注意**：`seed-orders` 要写进"支付时间"字段（可回填到 30 天前），否则日报表只有今天一条柱。
> 这两个接口必须用 `@Profile("demo")` 隔离，并在 README 里标注"生产禁用"——答辩被问到时，这是个展示工程素养的细节。

### 5.3 演示前 3 分钟检查清单

1. `POST /demo/reset` → 回到干净状态
2. 确认库存预警里有 2 个 SKU 是"不足"（提前把安全库存设高）
3. 确认会员"张三"余额充足、"李四"已过期（演示会员卡过期被拒）
4. 确认有 300 笔历史订单（报表有曲线）
5. 打印测试页打一张，确认打印机在线

## 8. 答辩时怎么讲这个设计

老师大概率会问："**你们没有真实的采购和支付，是不是做了个玩具？**"

准备好的回答：

> "我们是单系统闭环设计。上游的采购、供应商、人事、支付网关都不在本系统边界内，因此我们把它们的**结果**收敛为管理端的录入动作——经理补货，库存就增加，并生成单据与流水。**入口是简化的，但入口之后的一致性没有简化**：库存采用预占/释放/实扣三态加乐观锁，支付回调用唯一索引做幂等，订单有完整状态机，优惠按行分摊以保证退货金额正确。这四处是我们花时间最多的地方，也是这套系统真正的设计含量。"

三个要点：**边界说清楚**（不在我范围内，不是我没做）、**入口简化但内核完整**、**把时间花在一致性上**（这才是软件工程课要考的）。
