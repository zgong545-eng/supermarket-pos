## 2. 仓库与工程结构

采用**单仓多工程**（组长建仓后开放权限），好处是接口定义、SQL 脚本、文档与代码同版本演进。

```
sams-cashier/
├── README.md                    # 环境、启动、账号、常用命令
├── docs/                        # 00 01 02 三份文档 + api/ + db/
├── deploy/
│   ├── docker-compose.yml       # mysql + redis + server + nginx
│   ├── nginx.conf
│   ├── init.sql                 # 建库建表（由 Flyway 脚本汇总生成）
│   └── demo-data.sql            # 演示数据：8 分类 / 60 SKU / 3 会员 / 2 活动 / 5 券
├── server/                      # 后端（单 Maven 模块，按包分域）
│   ├── pom.xml
│   └── src/main/
│       ├── java/com/sams/cashier/
│       │   ├── CashierApplication.java
│       │   ├── common/          # 【A】统一响应、异常、常量、工具、金额
│       │   ├── security/        # 【A】JWT、过滤器、权限注解、数据范围
│       │   ├── infra/           # 【A】事件总线、定时任务、文件、缓存
│       │   └── module/
│       │       ├── auth/        # 【A】M01
│       │       ├── system/      # 【A】M13
│       │       ├── product/     # 【B】M02
│       │       ├── stock/       # 【B】M03
│       │       ├── member/      # 【D】M04
│       │       ├── promotion/   # 【D】M05
│       │       ├── order/       # 【C】M06
│       │       ├── payment/     # 【C】M07
│       │       ├── pos/         # 【C】M08
│       │       └── report/      # 【F】M09
│       └── resources/
│           ├── application.yml  # 本地配置
│           ├── application-dev.yml
│           └── db/migration/    # Flyway：V1__init.sql、V2__product.sql ...
├── web-pos/                     # 【E】收银端
├── web-admin/                   # 【F】管理端
└── web-member/                  # 【E】会员端
```

**每个 `module/xxx` 内部固定 7 个包，不许自创结构：**

```
module/order/
├── controller/     OrderController、RefundController
├── service/        OrderService（接口）
│   └── impl/       OrderServiceImpl
├── domain/         Orders、OrderItem（实体）
├── mapper/         OrdersMapper、OrderItemMapper
├── dto/            入参：CreateOrderDTO、RefundDTO
├── vo/             出参：OrderVO、OrderDetailVO
└── convert/        MapStruct 或手写转换
```

**四条硬约束（Code Review 直接打回）：**

1. Controller **不写业务**，只做参数校验 + 调 Service + 包 Result。
2. 跨模块**只调对方的 Service 接口**，绝不允许 A 模块的 Mapper 出现在 B 模块里。
3. 实体 `domain` 不出现在 Controller 出参里，必须转 VO（防止密码、成本价泄露）。
4. 写操作先进 Service 再进 Mapper，**`@Transactional` 只加在 Service 实现类的写方法上**。

## 3. 全局编码契约（第 2 周必须冻结）

这些是"全组共用的地基"，由 A 在第 2 周一次性交付到 `common` 与 `security` 包，其他人只允许使用、不允许各写一套。

### 3.1 统一响应

```java
public class Result<T> {
    private int code;        // 0 = 成功，非 0 = 业务错误
    private String message;
    private T data;
    private String traceId;  // 链路追踪，出问题按这个查日志
}
```

### 3.2 错误码分段

| 段位 | 领域 | 示例 |
|---|---|---|
| `1xxxx` | 通用（参数、系统） | 10001 参数校验失败 |
| `2xxxx` | 认证与权限 | 20001 未登录、20003 无权限、20004 越权访问 |
| `3xxxx` | 商品与库存 | 30001 商品不存在、30011 库存不足 |
| `4xxxx` | 交易与支付 | 40001 订单不存在、40012 订单状态不允许此操作、40021 支付单重复 |
| `5xxxx` | 会员与营销 | 50001 会员已过期、50011 券不可用、50012 不满足使用门槛 |

**约定**：所有业务失败必须抛 `BizException(code, message)`，由全局处理器转 `Result`；**禁止**在 Controller 里 `try-catch` 后返回自定义结构。

### 3.3 金额、时间、主键

| 项 | 规范 | 原因 |
|---|---|---|
| 金额 | 一律 `long`，单位**分**；DB 用 `bigint` | 浮点会累加出误差，退货必然算错 |
| 数量 | 称重商品用 `decimal(10,3)`（克/千克），计件用 `int` | 称重精度需要 |
| 时间 | `LocalDateTime`，DB `datetime`，JSON `yyyy-MM-dd HH:mm:ss` | 全组统一时区东八区 |
| 主键 | `bigint` 自增；**业务单号单独生成**（如 `SO20261020000001`） | 自增 ID 不暴露业务量，单号便于人工核对 |
| 状态 | 用 `String` 枚举码（`CREATED/PAID/...`），不用魔法数字 | 可读性 + 前端可直接判断 |

### 3.4 单号规则（收银员与经理都要认这个号）

| 类型 | 前缀 | 示例 |
|---|---|---|
| 销售订单 | `SO` | SO20261020000001 |
| 支付单 | `PY` | PY20261020000001 |
| 退款单 | `RF` | RF20261020000001 |
| 入库单 | `IN` | IN20261020000001 |
| 盘点单 | `CK` | CK20261020000001 |
| 班次 | `SH` | SH20261020000001 |

### 3.5 事务与幂等

- **事务边界**：一个用例一个事务，落在 Service 方法上；**不做跨模块大事务**（如"下单 + 扣库存 + 加积分"），改用领域事件在事务提交后处理，失败由对账兜底。
- **幂等**：所有"创建"接口接收 `requestId`（前端 UUID），Redis `setnx` 5 分钟；支付回调额外用 `payment.channel_trade_no` 唯一索引兜底。
- **并发**：库存扣减用乐观锁 `UPDATE stock SET ... WHERE version = ?`，影响行数为 0 时重读重试，最多 3 次。

### 3.6 权限注解

```java
@RequirePerm("stock:adjust")            // 接口级权限
@RequirePerm(value = "order:refund", scope = Scope.SELF)  // 叠加数据范围
```

`memberId` / `cashierId` **一律从 Token 解析**，禁止从请求参数取——这是防越权（IDOR）的唯一可靠做法。

## 5. 开发批次：谁能先开工

依赖关系决定批次。**同一批次内的模块可以并行，不同批次有强先后。**

| 批次 | 周次 | 内容 | 可并行的人 |
|---|---|---|---|
| **B1 地基** | 第 2–3 周 | `common` + `security` + M01 + M13 + 工程骨架 + Flyway + `docker-compose` | A（主）、全员等她的契约 |
| **B2 主数据** | 第 3–4 周 | M02 商品 + M04 会员 | B、D 并行；E/F 起前端壳 + Mock |
| **B3 能力** | 第 4–6 周 | M03 库存 + M05 促销 | B、D 并行 |
| **B4 交易** | 第 4–7 周 | M06 订单 + M07 支付 + M08 收银作业 | C 主；B 支援支付渠道 |
| **B5 呈现** | 第 6–9 周 | M10 + M11 + M12 + M09 | E、F 主；A 收尾联调 |

**关键排期技巧（务必执行）：**

- **B4 不必等 B3 完成**。订单服务在第 4 周就可以开写，用**接口 + 假实现**挡在库存、促销前面（`StockService` 先返回固定值，`PromotionEngine` 先返回 0 优惠）。第 6 周再把真实实现接上。这样 C 不会空转 2 周。
- **前端从第 3 周就开工**，靠 OpenAPI 生成的 Mock 数据做页面，不等后端。否则 E、F 前 5 周无事可做——这是学生项目最常见的浪费。
- **第 6 周末必须打通端到端收银**（MS2）。这条卡点不达，后面全部顺延，组长要提前两周盯 C 和 E。

## 6. 六人分工

### 6.1 分配原则

1. **主责唯一**：每个包只有一个 owner，`git blame` 能查到人。
2. **按人天配平，不按模块个数配平**：总 163 人天，人均 27.2，控制在 ±10%。
3. **难度与经验匹配**：较难模块给经验者，简单模块作新手成长入口。
4. **前后端不跨界**：主责端固定，减少上下文切换；跨端靠"支援人天"显式调度。
5. **关键路径双人可接力**：M06/M07 与 M11 各有备份人，防单点失联。

### 6.3 分工的可执行细节（拿到就能开工）

**A · 组长/架构（24 人天）**

- 第 1 周：建仓、`README`、`docker-compose`、目录骨架、`Result` / `BizException` / 错误码表 / `Money` 工具；
- 第 2 周：`security`（JWT 签发与校验、`@RequirePerm` 切面、`dataScope` 拦截）、`auth` 登录与刷新、Flyway `V1__init.sql`；
- 第 3 周：`system`（门店/设备/字典/参数）；**发布 OpenAPI 门面（不写全部接口，只定规范与示例）**；
- 第 4–8 周：联调支持、Code Review、每周集成、性能问题排查；
- 第 9–10 周：部署脚本、答辩材料。
- **对全组的输出承诺**：第 2 周末前，任何人新建一个 Controller 都能直接返回 `Result`、能加权限注解、能在 Swagger 上看到自己接口。

**B · 后端主数据（28 人天）**

- M02（第 3–4 周）：SPU/SKU 两级模型、分类树、条码、改价留痕、Excel 导入（EasyExcel）、价签数据；
- M03（第 4–6 周）：库存台账（`on_hand/locked/available/version`）、入库/报损/盘点单据、库存流水、预占与释放、预警；
- 支援 C（第 6 周，4 人天）：`PayChannel` 的现金与储值两个实现；
- **对全组的输出承诺**：`stock:lock(n)` / `stock:release(n)` / `stock:commit(n)` 三个原子接口，供订单直接调用；**必须附带 50 并发压测脚本**，否则视为未完成。

**C · 后端交易（28 人天）**

- M06（第 4–6 周）：购物车、下单、订单状态机（表驱动）、价格与成本快照、取消、整单/部分退货、可退量校验、`requestId` 幂等；
- M07（第 5–7 周）：支付单、`PayChannel` 适配器（现金/模拟微信/模拟支付宝/储值）、回调幂等、退款、对账脚本；
- M08（第 6–7 周）：开班/交班对账、挂单池、称重码解析、小票数据组装；
- **对全组的输出承诺**：第 4 周末给出 `POST /order/create` 与 `POST /pay/create` 的**可用实现 + 冻结契约**，E 的 POS 靠它联调。

**D · 后端营销（25 人天）**

- M04（第 3–5 周）：会员注册、年费卡/储值卡、等级、积分累计与抵扣、储值流水、会员码（60 秒刷新）；
- M05（第 5–7 周）：活动 CRUD、券模板与发放、**纯函数优惠引擎**、按行分摊、退货分摊回溯、券核销与回滚；

## 8. "写完了"的标准（DoD）

避免"我觉得做完了"的争论，用清单判定。

**一个后端接口算完成，必须同时满足 7 条：**

1. 有 OpenAPI 注释，Swagger 上能看到并能调通；
2. 有权限注解，越权访问返回 `20003/20004`；
3. 参数校验（`@Valid` + 业务校验），错误走 `BizException` 统一码；
4. 金额用 `long` 分，不出现 `double/float`；
5. 写操作有事务，跨模块用事件而非直接调 Mapper；
6. 关键路径有单测（下单、退款、预占、算价必须覆盖）；
7. Postman 集合里有对应请求，且已跑通。

**一个前端页面算完成，必须同时满足 6 条：**

1. 真实接口联调通过（不是只跑 Mock）；
2. 加载态、空态、错误态三种状态都有；
3. 权限控制：无权限的按钮不渲染或置灰；
4. 危险操作二次确认；
5. 1080p 与 1366×768 两种分辨率不串版；
6. 关键交互可键盘操作（POS 强制）。

## 9. Code Review 清单（每次 PR 必看 10 条）

1. 事务边界对不对？有没有把远程调用/事件塞进事务？
2. 金额类型是 `long` 吗？有没有 `double` 混进来？
3. 身份是不是从 Token 取的？有没有信前端传的 `memberId`？
4. 有没有 N+1 查询？列表接口是否分页？
5. 创建类接口有没有幂等？
6. 异常是否走了统一码，而不是返回 500？
7. 关键操作有没有日志（订单号、金额、操作人）？
8. 状态变更是否经过状态机校验，而不是直接 `setStatus`？
9. SQL 有没有走索引（`where` 字段是否有索引）？
10. 有没有留下 `System.out.println`、注释掉的代码、`TODO` 无主？

## 附录 C：Git 规范

**分支**：`main`（保护，只接受 PR）← `feat/{模块}-{简述}`（如 `feat/order-state-machine`）

- `feat(order): 实现订单状态机与非法跃迁拦截`
- `fix(stock): 修复并发下 locked 未释放`
- `docs(api): 补充退款接口契约`

type 取值：`feat / fix / docs / style / refactor / test / chore`

**PR 要求**：标题写明模块与影响范围；描述里贴自测截图或 Postman 结果；至少 1 人 Review 通过才能合并。
