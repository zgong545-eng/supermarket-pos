## 0. 文档说明

### 0.1 定位

本文档不是需求说明书，也不是详细设计，而是**面向"可分工、可排期、可迭代、可评分"的工程大纲**。它要回答四个问题：

1. 系统由哪些模块组成，每个模块**负责什么、不负责什么**；

### 0.3 选题来源与业务定位

选题为《附件2》第 19 项「超市收银系统」，题目文档仅给名称、未附加功能约束，业务范围由本组界定：

系统面向**会员制仓储式超市**（参照山姆会员商店 Sam's Club）的**单店收银业务**。相比普通超市，会员制仓储店有三个特征直接决定设计重点：

| 业务特征             | 对本系统的设计要求                             |
| ---------------- | ------------------------------------- |
| 会员制准入（年费卡 / 储值卡） | 会员身份是交易的**强制前置条件**，会员中心属核心域，不是可选模块    |
| 大包装、批量采购、客单价高    | 单笔订单行少而金额高、退货复杂，**订单状态机与退款流程**必须严谨可追溯 |
| 会员价、券、多件折扣叠加密集   | 促销必须做成**独立可测的计算引擎**，不能散落在收银逻辑里        |
| 生鲜称重 + 扫码购       | 需支持**称重码、挂单、跨端共享购物车**等特殊输入形态          |

为控制课程作业规模，以下能力列为**可选加分项（P2）**，不进入主线排期：线上配送、多门店调拨、供应链采购、自助收银机固件对接、真实商户号支付（用模拟网关替代）。

### 0.4 术语表

| 术语        | 含义                              |
| --------- | ------------------------------- |
| SPU / SKU | 标准商品单元 / 库存量单位（同商品不同规格）         |
| POS       | Point of Sale，收银终端              |
| 挂单 / 取单   | 暂存当前订单，服务下一位顾客后再取回结算            |
| 交班        | 收银员结束班次时核对现金、电子支付、退款并封账         |
| 称重码       | 生鲜条码，形如 `2` + 商品码 + 重量或金额 + 校验位 |
| 盘点        | 核对实物与系统库存并生成差异调整单               |
| 会员码       | 会员身份动态二维码/条码，收银端扫码识别            |

## 1. 立项（10 分）

### 1.1 项目背景

超市收银是零售业最基础也最容易出错的环节：价格算错、优惠叠加错、库存对不上、交班账不平，任何一个环节出错都直接变成金钱损失。会员制仓储超市（如山姆）把"会员"作为交易前置条件，叠加年费卡、会员价、储值、优惠券、大件退货，业务复杂度远高于普通超市。

现有课程作业中的"超市管理系统"多停留在"商品 + 订单 + 用户"三表 CRUD。本项目希望在**课程可完成的规模内**，做出一个真正能跑通"识别会员 → 扫码称重 → 优惠试算 → 收款 → 扣库存 → 出小票 → 交班对账"完整闭环的系统，并把三端（会员、收银员、经理）的权限边界做清楚。

### 1.2 系统目标

| 目标   | 可验证的判定标准                               |
| ---- | -------------------------------------- |
| 业务闭环 | POS 能独立完成一笔含会员价 + 券 + 称重商品的收银，单笔 ≤30 秒 |
| 数据一致 | 100 笔并发下单不超卖；支付重复回调不重复扣款               |
| 角色隔离 | 三类角色越权访问全部被拦截（提供越权测试用例）                |
| 管理可用 | 经理能建商品、配活动、看日报，报表数据与订单明细可对上            |
| 工程规范 | 分层清晰、接口文档完备、可一键部署演示                    |

### 1.3 三类角色与业务场景

| 角色             | 终端      | 核心诉求                     | 权限特征               |
| -------------- | ------- | ------------------------ | ------------------ |
| 客户端会员 Customer | 手机 H5   | 查商品、看权益、查订单积分、领券         | 只能访问**自己的**数据      |
| 收银员 Cashier    | POS 收银台 | 快（≤30 秒/单）、准（零差错）、可挂单可退货 | 绑定当班门店与班次，受授权额度限制  |
| 经理/管理员 Manager | PC 管理端  | 管商品、管库存、配活动、看报表、管员工      | 门店级数据范围（dataScope） |
| 系统管理员 SysAdmin | PC 管理端  | 账号、角色、字典、日志、参数           | 不参与业务，仅配置与审计       |

**四条架构约束（写进代码规范，评审逐条确认）：**

- **R1** 收银员不能改价、不能删单，只能发起退货；超授权额度退款需经理端审批。
- **R2** 经理不能直接改库存数字，只能走入库/盘点/报损单据，保证库存有据可查。
- **R3** 客户端不参与库存扣减的最终裁决，线上下单与 POS 结算走**同一套订单服务**。
- **R4** 金额、数量、积分一律用整数（分/件/分）存储计算，禁止浮点参与结算。

### 1.4 技术选型基线

选型不是论证重点，但必须先行锁定，否则模块边界无法落地。

| 层次      | 基线方案                                                     | 备选                           |
| ------- | -------------------------------------------------------- | ---------------------------- |
| 后端      | Java 17 + Spring Boot 3 + Spring Security + MyBatis-Plus | NestJS / Django（组内技术栈强绑定时替换） |
| 数据库     | MySQL 8.0（Redis 用于会话、库存预占、促销缓存）                          | PostgreSQL                   |
| 会员客户端   | Vue 3 + Vant（H5，移动端优先）                                   | 微信小程序                        |
| 收银端 POS | Vue 3 + Element Plus（Web，全键盘操作，兼容扫码枪键盘模拟输入）              | Electron 桌面封装                |
| 管理端     | Vue 3 + Element Plus + ECharts                           | React + Ant Design           |
| 接口      | RESTful + JSON，JWT 鉴权，**OpenAPI 先行的契约开发**                | GraphQL（不推荐，抬高联调成本）          |
| 部署      | Nginx + Docker Compose 单机部署                              | 云服务器 / 本地演示                  |

**关键取舍：采用模块化单体，不做微服务拆分。** 理由：6 人 10 周，微服务的部署、联调、调试成本远超收益；模块边界通过代码分包与接口契约已经体现，答辩时作为"架构权衡"说明即可。

### 1.5 交付物与里程碑

| 里程碑      | 时点      | 验收标准                          |
| -------- | ------- | ----------------------------- |
| MS1 地基通  | 第 3 周末  | 三端能登录、商品可增删改查、接口文档可访问         |
| MS2 收银闭环 | 第 6 周末  | 扫码→识别会员→优惠试算→收款→扣库存→出小票，全链路跑通 |

| MS5 交付   | 第 10 周末 | 报告书、自评报告、使用说明书、演示视频、答辩 PPT 齐备 |

## 2. 可行性研究（10 分）

### 2.1 技术可行性

| 关键技术点        | 成熟度              | 结论                        |
| ------------ | ---------------- | ------------------------- |
| 三端 + 后端单体    | 高，主流框架范式成熟       | 可行，参考实现充足                 |
| 订单状态机 / 库存预占 | 中，需自研但模式固定       | 可行，乐观锁 + 事件驱动为常规方案        |
| 促销计算引擎       | 中，规则需自设计         | 可行，纯函数化 + 单测可覆盖           |
| 支付渠道对接       | 高（用模拟网关，不接真实商户号） | 可行，规避资质与资金风险              |
| 小票打印 / 扫码枪   | 中，依赖浏览器与硬件       | 基本可行，需第 3 周提前验证，并准备手工输入降级 |

**结论：技术上完全可行。** 唯一需要提前验证的是硬件交互（扫码枪键盘模拟、浏览器打印），已列为第 3 周风险验证项。

### 2.2 经济可行性

- 全部使用开源技术栈与免费工具（IDEA 社区版 / VS Code、MySQL、Git、Docker Desktop），**零软件采购成本**。
- 演示环境用组员个人电脑 + 本地 Docker，无需云服务器费用；若需外网演示，最低配云主机约 100 元/月，可由组费分摊。
- 人力为课程投入，不计成本。

**结论：经济上可行，直接成本趋近于零。**

### 2.3 操作可行性

- 收银员端界面参照真实 POS 布局（左侧扫码区、中间明细、右侧合计与支付），键盘快捷键与真实设备一致，**无需培训即可上手**；
- 管理端采用标准后台范式（查询区 + 表格 + 弹窗表单），符合管理者既有习惯；
- 会员端为移动 H5，扫码即用，无需安装 App。

**结论：操作上可行。**

### 2.4 进度可行性

6 人 × 10 周，按有效投入 3 人天/人/周计算约 180 人天，本方案估算 **163 人天**，留有约 10% 缓冲，可吸收联调与返工。

**结论：进度上可行，但关键路径（订单+支付+POS）没有余量，必须严格执行里程碑。**

### 2.5 风险与结论

| 风险           | 概率 | 影响 | 应对                                        |
| ------------ | -- | -- | ----------------------------------------- |
| 收银闭环延期（关键路径） | 中  | 高  | 第 4 周先做"现金支付"最小闭环，多渠道后置；E 与 C 第 5 周结对联调   |
| 促销规则越写越乱     | 高  | 中  | 引擎纯函数化 + 单测先行，规则配置化，禁止 Service 里堆 if-else |
| 库存并发超卖       | 中  | 高  | 乐观锁 + 预占模型；第 9 周 JMeter 50 并发压测并出报告       |
| 前端被接口阻塞      | 高  | 中  | OpenAPI 先行 + Mock 数据 + 自动生成类型，前端不等待后端     |
| 打印/扫码枪环境不通   | 中  | 中  | 第 3 周验证，准备虚拟打印机与手工输入降级                    |
| 成员进度不均       | 中  | 中  | 每周看板核对人天，I3 结束后做一次任务再平衡                   |
| 答辩演示环境故障     | 低  | 高  | 提前录演示视频 + Docker 一键启动脚本                   |

**综合结论：项目在技术、经济、操作、进度四方面均可行，予以立项。** 最大风险集中在交易链路，需以"最小闭环先行"的策略推进。

### 3.2 核心业务流程

**流程一：收银结算主链路（答辩必演示）**

```
POS 扫码 ──→ M06 建单（明细入购物车）
           ──→ M04 识别会员（等级/券/积分）
           ──→ M05 试算（会员价→活动→券→积分抵扣）← 返回逐行优惠明细
           ──→ 收银员确认应收 → M07 发起支付
           ──→ 支付成功回调 → M06 置为已支付（事务内）
                 ├─ 发布 OrderPaidEvent
                 ├─→ M03 扣减库存（locked→on_hand）
                 ├─→ M04 累计积分、核销券、扣储值
                 └─→ M09 写销售事实（供预聚合）
           ──→ M08 生成小票 → POS 打印
```

**流程二：退货**

```
POS 选单 → M06 校验可退量（≤ 已购 − 已退）
        → M05 按原分摊比例算应退金额（禁止重算优惠）
        → 超额度则 M08 发起经理授权
        → M07 原路退款（储值回充余额）
        → M06 更新状态（部分退货 / 已退货）
        → OrderRefundedEvent → M03 退货入库、M04 扣回积分、M09 冲减销售额
```

**流程三：盘点**

```

## 4. 形式化说明技术运用（10 分）

> 这一项最容易丢分，也最容易拿分：不需要用 Z 或 B 方法写整篇规格，只需**在关键处用形式化手段把"不能出错"的地方说清楚**，并说明它如何落到代码与测试里。

### 4.1 技术选型与理由

| 技术                 | 用在哪            | 为什么选它                           |
| ------------------ | -------------- | ------------------------------- |
| 有限状态机（FSM，状态转移表）   | 订单、支付单、会员卡、盘点单 | 状态多、非法跃迁就是事故，表格化后可**直接生成表驱动测试** |
| 一阶逻辑不变式（Invariant） | 库存、金额、退货量      | 用等式把"守恒关系"钉死，任何操作前后都必须满足        |
| 契约式设计（前置/后置条件）     | 促销计算、结算、退款     | 输入输出可断言，配合单测直接验证                |
| 集合与关系描述            | 权限模型           | RBAC 本质是集合运算，用集合式表达比文字更精确       |
| UML 状态图 / 顺序图 / 类图 | 全流程表达          | 图形化补充，作为形式化表格的可视化对照             |

**明确不采用**：Z 语言、B 方法、Petri 网。理由是学习成本与课程周期不匹配，且上述四种手段已能覆盖本项目全部关键约束——这个取舍本身就是"形式化技术运用"的论证内容，答辩时要讲。

### 4.2 订单状态机的形式化描述

定义状态集 `S = {CREATED, PAID, COMPLETED, CANCELLED, REFUNDING, PART_REFUNDED, REFUNDED}`，  
事件集 `E = {pay, complete, cancel, applyRefund, refundDone}`，  
转移函数 `δ: S × E → S ∪ {⊥}`（`⊥` 表示拒绝）：

| 当前状态 \ 事件            | pay          | complete  | cancel    | applyRefund | refundDone               |
| -------------------- | ------------ | --------- | --------- | ----------- | ------------------------ |
| CREATED              | PAID         | ⊥         | CANCELLED | ⊥           | ⊥                        |
| PAID                 | ⊥（幂等返回 PAID） | COMPLETED | ⊥         | REFUNDING   | ⊥                        |
| COMPLETED            | ⊥            | ⊥         | ⊥         | REFUNDING   | ⊥                        |
| REFUNDING            | ⊥            | ⊥         | ⊥         | ⊥           | PART_REFUNDED / REFUNDED |
| PART_REFUNDED        | ⊥            | ⊥         | ⊥         | REFUNDING   | REFUNDED                 |
| CANCELLED / REFUNDED | ⊥            | ⊥         | ⊥         | ⊥           | ⊥（终态）                    |

**不变式（每个操作前后必须成立）：**

- `INV-O1（金额守恒）`：`paid_amount + discount_amount = payable_amount`，且 `payable ≥ 0`
- `INV-O2（退货不超量）`：`∀item: refunded_qty(item) ≤ qty(item)`
- `INV-O3（支付必然性）`：`status ∈ {PAID, COMPLETED, REFUNDING, PART_REFUNDED, REFUNDED} ⇒ ∃ 成功支付单 p, p.order_id = order.id`
- `INV-O4（终态不可逆）`：`status = CANCELLED ⇒ 库存预占已全部释放`

**落地方式**：把上表直接写成代码里的 `Map<状态, Map<事件, 目标状态>>`，用一张**表驱动单元测试遍历 7×5=35 个组合**，断言其中 9 个合法转移成功、26 个非法转移抛异常。答辩时展示这张测试报告，比讲十句"我们考虑了状态机"有说服力。


### 4.3 库存守恒的形式化

对任意 `SKU × 门店`，定义 `on_hand`（在库）、`locked`（预占）、`available`（可售）：

```
INV-S1   on_hand = available + locked
INV-S2   available ≥ 0 ∧ locked ≥ 0 ∧ on_hand ≥ 0
INV-S3   所有变更必须存在单据 b 与流水 f，且 f.before + f.delta = f.after
```

四类操作对三元组的影响（可逐条转成单测）：

| 操作 | available | locked | on_hand |
|---|---|---|---|
| 预占 lock(n) | −n | +n | 0 |
| 释放 release(n) | +n | −n | 0 |
| 支付实扣 commit(n) | 0 | −n | −n |
| 入库 inbound(n) | +n | 0 | +n |

**由此可直接导出"超卖不可能"的论证**：`commit(n)` 的前提是 `locked ≥ n`，而 `locked` 只可能由 `lock(n)` 从 `available` 转入，且 `INV-S2` 保证 `available ≥ 0`，故任意时刻 `Σ已提交 ≤ 初始 on_hand + Σ入库`。这条推导写进报告书，是"形式化技术运用"的加分点。

### 4.4 促销计算的契约式规约

```
函数  calc(cart, member, now) → Result
前置  PRE:  cart.items ≠ ∅
            ∧ ∀i: i.qty > 0 ∧ i.unit_price ≥ 0
            ∧ (member = ⊥ ∨ member.status = ACTIVE)
后置  POST1: result.payable = Σ(item.subtotal) − Σ(result.discounts.amount)
后置  POST2: result.payable ≥ 0
后置  POST3: ∀d ∈ result.discounts: d.reason ≠ "" ∧ d.rule_id 可追溯
后置  POST4: Σ(item.discount_share) = Σ(result.discounts.amount)   ← 分摊可还原
```

`POST4` 是退货正确性的数学基础：只要整单优惠被完整分摊到行，退货时按行分摊额退就不会算错。这条不变式必须写成断言并在单测中验证。

### 4.5 权限模型的集合描述

```
设 U 用户集，R 角色集，P 权限集（元素为 (资源, 动作) 二元组）
角色权限映射  rp : R → 2^P
用户角色映射  ur : U → 2^R
用户权限集    Perm(u) = ∪ { rp(r) | r ∈ ur(u) }
访问判定      can(u, res, act) ⇔ (res, act) ∈ Perm(u) ∧ scope(u) ⊇ scope(target)
其中 scope ∈ {ALL, STORE, SELF}，且 ALL ⊇ STORE ⊇ SELF
```

用它可以直接论证 **R1（收银员不能改价）**：`(price, update) ∉ Perm(cashier)`，因为收银员角色未被授予该二元组——安全约束从"人记住"变成"模型保证"。

## 5. 总体设计（15 分）

### 5.1 架构设计

**分层架构 + 前后端分离 + 领域模块化**，依赖单向向下：

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层 / 表现层                                                │
│   会员 H5        收银 POS        管理端 PC     （三套独立前端） │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS + JSON + JWT
┌───────────────────────────┴──────────────────────────────────┐
│ 接口层 Controller                                              │
│ 参数校验 · 鉴权拦截 · 权限注解 · 统一响应 · 全局异常 · 限流      │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────┴──────────────────────────────────┐
│ 应用服务层 Application Service                                 │
│ 用例编排 · 事务边界 · 跨域协作 · DTO 转换                        │
│ SaleService / RefundService / StockService / PromotionEngine … │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────┴──────────────────────────────────┐
│ 领域层 Domain                                                  │
│ 实体 · 值对象 · 领域服务 · 领域事件（库存扣减、积分累计、审计）  │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────┴──────────────────────────────────┐
│ 数据访问层 Repository / Mapper + MySQL + Redis                  │
└──────────────────────────────────────────────────────────────┘
```

**分层约束（禁止反向依赖）：**
- 只允许上层调用下层；领域层不得引用 Controller 或 DTO。
- **跨域解耦用领域事件**：支付成功发布 `OrderPaidEvent`，库存、积分、报表各自订阅，订单服务不直接调用库存 Mapper。
- 三套前端共享一份由 OpenAPI 生成的 API 类型定义与错误码表，禁止各自手写。

**部署视图：**

```
        浏览器 / 手机

会员H5    管理端      POS 静态资源

### 6.3 关键算法

| 算法 | 要点 |
|---|---|
| 优惠分摊 | 整单优惠按行金额占比分摊，**末行承接舍入差额**，保证 `Σ分摊 = 整单优惠` |
| 退货金额 | 按行 `discount_share / qty × 退货数量` 计算，尾差同样末次调整 |
| 现金找零 | 从大到小贪心 + 分币处理，输出各面额张数 |
| 称重码解析 | 前缀 2 + 商品码 + 重量/金额 + 校验位；校验失败转手工录入并标记 |
| 乐观锁重试 | `UPDATE ... WHERE version = ?`，影响行数 0 则重读重试，最多 3 次后转失败提示 |
| 幂等 | 支付回调按 `channel_trade_no` 唯一索引 + 状态机判定，重复请求返回首次结果 |

### 6.4 异常与状态处理

统一异常体系 `BizException(code, message)`，全局处理器转标准响应；**所有非法状态跃迁返回明确业务码**（如 `40012 订单状态不允许此操作`），前端据此给收银员可读提示，而不是"系统错误"。

### 6.6 模块难度评估

**评估方法**：五个维度各打 1–5 分，取算术平均得**难度值**，映射档位（`<2.5 简单`、`2.5–3.4 中等`、`≥3.5 较难`）。

| 维度 | 含义 | 高分意味着 |
|---|---|---|
| 业务规则复杂度 | 需建模的约束、状态、例外 | 规则说不清，返工率高 |
| 技术实现复杂度 | 并发、事务、算法、架构模式 | 需查资料与反复调试 |
| 联调依赖度 | 依赖多少模块、接口是否易变 | 等待与被阻塞风险大 |
| 数据一致性要求 | 出错是否造成金额/库存错误 | 必须幂等、事务、对账 |
| 界面交互工作量 | 页面数、焦点/键盘/打印等细节 | 耗时长但技术门槛低 |

> **难度值 ≠ 工作量。** 管理端页面多、单页简单，属"工作量大人天多但难度中等"；订单中心页面少、规则严，属"难度最高"。分工时两个指标都要看。

**评级依据：**

**简单档（2 个）**
- **M02 商品（2.4）**：标准 CRUD + 树形分类 + Excel 导入，无并发与状态机；唯二注意点是"改价留痕"与"称重商品标记"，均为单表设计。适合交给经验最少的成员建立信心。
- **M13 系统管理（2.2）**：字典、参数、门店、设备四张配置表，纯表格页；唯一技术点是参数变更要让 M03/M08 即时读到，用缓存刷新即可。

**中等档（6 个）**
- **M01 平台权限（3.0）**：单点技术不难（Spring Security + JWT 有成熟范式），但**联调依赖 5 分**——它是全组前置，接口设计失误会让 12 个模块返工。评为"中等难度、最高风险"，必须组长做。
- **M04 会员（2.8）**：实体多（会员、卡、积分流水、钱包流水）但规则线性；积分与储值有金额一致性隐患，需事务 + 流水兜底。
- **M08 收银作业（3.4）**：挂单池与交班对账逻辑偏细，对账口径一错就演示不出"账平"，处在中等上沿，实际接近较难。
- **M09 报表（3.2）**：SQL 聚合与图表配置工作量集中，难点在**口径统一**与"不能大表实时联查拖慢收银"，需预聚合表 + 定时任务。
- **M10 客户端（2.8）/ M12 管理端（2.8）**：技术难度低（标准表单与列表），但**界面交互 5 分**——管理端 10 个页组、客户端 8 个页面，是纯工作量密集区。

**较难档（5 个）**
- **M06 交易订单（4.2，全系统最高）**：订单状态机、价格快照、可退量控制、幂等下单四类问题叠加，且被 8 个模块依赖。**必须由最强后端承担，必须最早冻结契约。**
- **M07 支付结算（4.0）**：多渠道适配、回调幂等、退款原路返回、对账差异处理。渠道虽用模拟网关，但"支付成功而订单没改"这类缺陷极难排查，必须配唯一索引与对账脚本。
- **M03 库存（3.8）**：核心是**并发下的预占与回滚**，学生最容易写出超卖。乐观锁重试 + 单据流水是必需设计，不是加分设计。
- **M05 促销（3.8）**：业务规则 5 分。叠加顺序、互斥优先级、整单优惠按行分摊、退货按原分摊退——四条规则互相纠缠，一旦散落在结算代码里就再也改不动，必须做成纯函数引擎并写单测。
- **M11 POS（4.0）**：界面 5 分叠加实时性（≤30 秒/单），扫码枪焦点管理、弹窗层级、小票打印、快捷键都是真实工程细节；同时它是所有后端接口的最终集成点，**一个接口没通，演示就断在台上**。

**难点与对策：**

| 难点 | 后果 | 对策 |
|---|---|---|
| 订单 + 支付一致性与幂等 | "付了钱没订单"或重复扣款 | 唯一索引 + 状态机 + 对账脚本 + 双人评审 |
| 库存并发预占 | 超卖 | 乐观锁 + 预占模型 + 50 并发压测 |
| 促销分摊与退货回溯 | 退款金额错 | 引擎纯函数化 + 分摊额落库 + 20 条边界单测 |
| 三角色越权 | 数据泄露，安全扣分 | Token 取身份 + 接口权限注解 + 越权测试用例 |
| 前端堵在接口上 | 联调期集中爆炸 | OpenAPI 先行 + Mock + 第 6 周端到端闭环 |

**分配原则：**
1. **主责唯一**——每模块只有一个主责人，避免"共同负责 = 无人负责"。
2. **按人天配平，不按模块个数配平**——总 163 人天，人均 27.2，控制在 ±10%。
3. **难度与经验匹配**——较难模块交给经验者，简单模块作为新手成长入口。
4. **前后端不跨界**——每人主责端固定，减少上下文切换，跨端由"支援人天"显式调度。

**必测边界用例（答辩时可展示）：**
1. 库存仅剩 1 件时 10 人同时下单 → 只成功 1 单；

3. 整单优惠 3 类叠加后按行退货 → 退款额加总等于实付；
4. 收银员尝试改价/查他人订单 → 均被拒绝。

### 8.1 可维护性设计（已落到架构里）

| 措施 | 体现 |
|---|---|
| 分层与分包 | 按域分包，模块间只通过 Service 接口与事件交互，改一个模块不牵动全局 |

## 9. 课程设计总结

### 9.1 分工与个人贡献

报告书要求逐评分项填写"参与人员"，建议按下表填写，做到**可核查**：

| 评分项 | 主要参与 | 贡献说明（写进报告书） |
|---|---|---|
| 立项 | A、全员 | A 定范围与目标，全员提供业务场景与竞品调研 |
| 可行性研究 | A、B、E | A 汇总；B 论证技术与性能；E 论证硬件与操作可行性 |
| 需求分析 | D、A | D 主笔用例与非功能需求；A 汇总评审 |
| 形式化说明 | C、B | C 写订单状态机与金额不变式；B 写库存守恒 |
| 总体设计 | A、C | A 架构、模块划分、依赖；C 接口契约 |
| 详细设计 | B、C、D | 各自模块的类图、时序、算法 |
| 实现 | 全员，E 汇总 | 按 7.3 分工表逐项列 |
| 维护 | F、A | F 主笔；A 提供部署与备份方案 |
| 总结 | A | 汇总各人复盘 |

### 9.2 预期难点复盘（结课后按实际填写）

1. **促销规则的耦合是最大陷阱**——最初想把优惠写在结算 Service 里，第 7 周发现退货算不对，重构成纯函数引擎后才稳定。教训：**规则密集处必须先做可测的独立单元**。
2. **接口没先行导致返工**——第 5 周订单接口字段改了两次，两个前端各改一遍。教训：**契约冻结不是形式主义**。
3. **库存预占比想象中难**——第一版直接扣 `on_hand`，并发测试立刻超卖。教训：**一致性要求高的地方，先用不变式想清楚再写代码**。

### 9.3 改进方向

- 补齐自助收银与扫码购的完整闭环；
- 引入消息队列做支付回调削峰（当前同步处理，压测下会成为瓶颈）；
- 报表从"预聚合 + 定时"升级为"宽表 + OLAP"，支持任意维度下钻；
- 增加自动化 UI 回归（Playwright），降低每次发版的人工回归成本。

## 附录 C：本大纲的使用方式

1. **开工前**——全组通读第 1、5 章，确认模块边界与依赖顺序，对"不做"清单逐条确认。
2. **分工时**——每人认领 7.3 表的一行，把主责模块的用例（3.1 编号）拆成自己的任务卡。
3. **每周**——对照 7.2 迭代计划与 MS 里程碑自查，偏差超 1 周立即上报组长。
4. **写报告书时**——按 0.2 对照表成章，形式化一节直接用第 4 章，维护一节直接用第 8 章。
5. **迭代时**——任何模块职责变化，先改本文档第 5 章再改代码，保证文档与实现同步。
6. **答辩前**——用 7.5 边界用例自测，用 7.6 脚本排练。
