## 1. 技术栈与工程结构

### 1.1 版本锁定（照抄，别自选）

| 项 | 版本 |
|---|---|
| JDK | 17.0.9 |
| Spring Boot | 3.2.x（注意 jakarta 包名，别抄 2.x 教程） |
| MyBatis-Plus | 3.5.5（用 `mybatis-plus-spring-boot3-starter`） |
| MySQL / Redis | 8.0.36 / 7.2 |

| Node / Vue / Vite | 20.x / 3.4 / 5.x |
| Element Plus / Vant / ECharts | 2.6.x / 4.8.x / 5.4.x |

### 1.2 目录结构

```
sams-cashier/
├── server/                    # 后端（单 Maven 模块，按域分包）
│   └── src/main/java/com/sams/cashier/
│       ├── common/            # 【A】Result、异常、错误码、Money
│       ├── security/          # 【A】JWT、过滤器、权限注解、dataScope
│       ├── infra/             # 【A】事件、定时、文件、缓存
│       └── module/{auth,system,product,stock,member,promotion,order,payment,pos,report}/
├── web-pos/                   # 【E】收银端
├── web-member/                # 【E】会员端 H5
├── web-admin/                 # 【F】管理端
├── deploy/                    # docker-compose、nginx、demo 数据脚本
└── docs/                      # 本文档
```

每个 `module/xxx` 固定 7 个包：`controller / service / service/impl / domain / mapper / dto / vo / convert`。

### 1.3 四条硬约束（违反直接打回）

1. Controller 不写业务，只做校验 + 调 Service + 包 Result；
2. 跨模块**只调对方的 Service 接口**，禁止 A 模块的 Mapper 出现在 B 模块；
3. 实体不出现在 Controller 出参里，必须转 VO（防成本价、密码泄露）；
4. `@Transactional` 只加在 Service 实现类的写方法上，不做跨模块大事务（用事件）。

## 2. 公共契约（A 在 W2 末一次性交付）

| 项 | 规范 |
|---|---|
| 统一响应 | `Result{code, message, data, traceId}`，`code=0` 为成功 |
| 错误码 | `1xxxx` 通用 / `2xxxx` 权限 / `3xxxx` 商品库存 / `4xxxx` 交易支付 / `5xxxx` 会员营销 |
| 金额 | **一律 `long`，单位分**；DB `bigint`；禁止 `double` |
| 称重数量 | `decimal(10,3)` |
| 时间 | `LocalDateTime`，`yyyy-MM-dd HH:mm:ss`，东八区 |
| 单号 | `SO/PY/RF/IN/LS/CK/SH + yyyyMMdd + 5位序列` |
| 幂等 | 创建类接口收 `requestId`，Redis `setnx` 5 分钟；支付回调加 `channel_trade_no` 唯一索引 |
| 并发 | 库存 `UPDATE ... WHERE version=?`，失败重读重试 3 次 |
| 权限 | `@RequirePerm("stock:replenish")`；`memberId/cashierId` **从 Token 取**，禁止前端传 |

## 4. 六人分工与难度（核心）

### 4.1 分工原则

1. 主责唯一（每包一个 owner，`git blame` 能定位到人）；
2. 按**人天 + 难度**双维度配平，不是只看人天；
3. 难活给经验者，简单模块作新手入口；
4. 前后端不跨界，跨端靠显式"支援人天"；
5. 关键路径双人可接力（C 与 E 各有备份）。

### 4.2 分工总表

| 成员 | 角色 | 主责 | 人天 | 综合难度 | 适配人选 |
|---|---|---|---|---|---|
| **A** | 组长 · 架构 | M01 平台权限、M13 系统管理、部署与集成 | 30 | 3.6 较难 | 组织力强、能推进、技术中上即可 |
| **B** | 后端 · 主数据 | M02 商品、M03 库存、支付渠道实现 | 30 | 3.8 较难 | 严谨、爱较真、能坐住调 bug |
| **C** | 后端 · 交易 | M06 订单、M07 支付核心、M08 交班对账 | 31 | **4.6 最难** | **组内技术最强**，做过并发或支付 |
| **D** | 后端 · 营销 | M04 会员、M05 促销、M08 挂单与称重 | 31 | 3.6 较难 | 逻辑/数学思维好，能设计规则 |
| **E** | 前端 · POS 与会员端 | M11 POS、M10 客户端 | 30 | **4.0 较难** | 手快、抗压、**愿意上台演示** |
| **F** | 前端 · 后台与报表 | M12 管理端、M09 报表、测试与文档 | 30 | 3.4 中等 | 耐心、细致、新手友好但量大 |

### 4.3 每人难度画像

**注意：这里评的是"这个人承担的这一摊活有多难"，与模块难度不同——它把责任压力、调试难度、上台暴露度也算进去了。**

| 维度 | 含义 | 高分意味着 |
|---|---|---|
| 技术难度 | 需要掌握的最难技术点 | 不会就要现学，学不会就卡住 |
| 认知负荷 | 模块数量与切换成本 | 一天换三个上下文，容易漏 |
| 关键路径压力 | 卡住会不会拖全组 | 你延期 = 全组延期 |
| 调试难度 | 出错后好不好查 | 并发/金额/打印类问题极难复现 |
| 上台暴露度 | 演示时暴露在老师面前的程度 | 一出错全场看见 |

| 成员 | 技术 | 认知 | 关键路径 | 调试 | 暴露 | 综合 | 档位 |
|---|---|---|---|---|---|---|---|
| A | 3 | **4** | **5** | 3 | 3 | 3.6 | 较难 |
| B | 4 | 3 | 4 | **5** | 3 | 3.8 | 较难 |
| **C** | **5** | 4 | **5** | **5** | 4 | **4.6** | **最难** |
| D | 4 | 3 | 4 | 4 | 3 | 3.6 | 较难 |
| **E** | 3 | 3 | **5** | 4 | **5** | **4.0** | 较难 |
| F | 3 | **5** | 3 | 3 | 3 | 3.4 | 中等 |

**逐人解读：**

**A（3.6）——不难在技术，难在责任。**
技术上限不高（Spring Security 有成熟范式），但**联调依赖 5 分**：他一个人延期，五个人空转。认知负荷高——同时管平台、配置、部署、集成、评审、答辩六件事。
- 学习曲线：陡在"第一次要定架构和契约"，但这是组长必须经历的。
- 风险：接口设计失误会让 12 个模块返工。
- 可替换性：**低**。换人要重走一遍契约对齐。

**B（3.8）——难在"数字不能错"。**
库存预占是学生最容易写出超卖的地方，而超卖**在演示时看不出来**（要么压测才发现，要么事后对账才发现），所以调试难度 5。
- 学习曲线：乐观锁与三态流转需要想清楚，但代码量不大。
- 风险：预占释放漏一处，库存就永远少了。
- 可替换性：**中**。逻辑一旦用不变式写清楚，别人能接手。

**C（4.6）——全组唯一"不能出错"的岗。**
订单状态机、价格快照、可退量、支付幂等，四处叠加；被 8 个模块依赖；出错直接是金额错（资损）。
- 学习曲线：**最陡**。状态机要用表驱动写，幂等要靠唯一索引，这两件事没做过就会写成"看起来对"的样子。
- 风险：**最高**。W4 卡点过不去，全组陪跑。
- 可替换性：**极低**。必须一次给对人。

**D（3.6）——难在"规则想得清不清"。**
优惠叠加顺序、互斥优先级、整单优惠按行分摊、退货按原分摊退——四条规则互相纠缠。规则想不清楚，代码越写越乱。
- 学习曲线：中。关键是"先设计再写"，别边写边想。
- 风险：分摊算错 → 退货金额错 → 演示当场被追问。
- 可替换性：**中**。引擎纯函数化之后，可换人维护。

**E（4.0）——难在"演示当天站台上"。**
技术上都是前端，但叠加了三件事：实时性（单笔 ≤30 秒）、硬件交互（扫码枪焦点、58mm 打印）、全场注视。
- 学习曲线：平缓但有暗坑——扫码枪等同键盘输入，AI 生成的代码多半处理不好焦点。
- 风险：**演示风险最高**。一个接口没通，台上就卡住。
- 可替换性：**低**。POS 的坑只有踩过的人知道。

**F（3.4）——不难，但量大。**
10 个页组 + 报表 + 测试 + 文档，认知负荷 5 分，但每一项都不需要深技术。
- 学习曲线：最平缓。**最适合新手或进度落后的人**。
- 风险：量堆不完会拖到 W7。
- 可替换性：**高**。页面按模板复制，换人也能接。

### 4.4 难度 × 人天四象限（怎么把难活给对的人）

```
        难度高
          │
   C 4.6  │  E 4.0
   (难+重) │  (难+重)
──────────┼──────────  人天多 →
   D 3.6  │  B 3.8
   A 3.6  │  F 3.4（量大人天多，但简单）
          │
        难度低
```

| 象限 | 成员 | 该怎么安排 |
|---|---|---|
| 高难度 · 高人天 | **C、E** | 必须给组内最强的两人，且**不能给他们加别的活** |
| 高难度 · 中人天 | **B、D** | 给严谨/逻辑好的人，允许慢一点，但不许糊弄 |
| 中难度 · 高人天 | **A、F** | A 是组长（责任重），F 给新手练手（量大但不难） |

**关键结论：人天均衡（都 30）不等于难度均衡。** C 和 E 的 30 人天含金量远高于 F 的 30 人天。补偿方式：
- C 不承担任何文档、测试、答辩材料；
- E 不承担任何后端任务；
- F 多承担测试与文档（本来就轻）；
- A 少担业务人天，但扛管理与集成。

### 4.5 均衡校验

| 成员 | 人天 | 偏差 | 综合难度 | 说明 |
|---|---|---|---|---|
| A | 30 | 0 | 3.6 | 业务略少，但含管理职责 |
| B | 30 | 0 | 3.8 | 含支援 C 的支付渠道 4 人天 |
| C | 31 | +3% | 4.6 | 最高难度，已扣除被支援部分 |
| D | 31 | +3% | 3.6 | 引擎需大量单测，留调试余量 |
| E | 30 | 0 | 4.0 | 两个前端工程 |
| F | 30 | 0 | 3.4 | 量最大，难度最低 |

人天标准差 ≈ 0.5（2%）；**难度标准差 ≈ 0.4，且分布与"人的能力"匹配**——这是这套分工真正的均衡点。

## 7. 课堂演示版口径

### 7.1 原则

> **凡是"等别人送数据进来"的地方，改成"经理在界面上自己填"。**
> 入口可以伪造，**账不能算错**。

| 可简化 | 不可简化 |
|---|---|
| 补货/报损/盘点 → 后台直接录入 | 库存预占三态 + 乐观锁 |
| 商品/会员/员工建档 → 后台录入 | 支付回调幂等 |
| 支付 → 模拟渠道 + 系统自触发回调 | 订单状态机 |
| 短信验证码 → 固定码或免验 | 优惠按行分摊 |
| 门店 → 单店 | — |

### 7.2 补货（管理端直接录入）

**三个入口**：库存预警列表行内"补货"按钮（演示用这个）→ 批量补货 → 补货记录页。

表结构：`stock_bill(type=INBOUND, source=MANUAL, status=CONFIRMED)` + `stock_bill_item(sku_id, qty, cost_price, amount)`。
**不建** `supplier`、`purchase_order`、审批流、到货确认——避免留下永远为空的字段。

七条规则要点：`qty>0` 且 ≤9999；进价缺省取上次进价；**提交即生效无审批**；事务内写单据+改库存+写流水；进价变化要更新 `sku.cost` 并留成本变更记录；`requestId` 幂等；权限 `stock:replenish`。

接口 4 个：`GET /stock/warning/list`、`POST /stock/replenish`、`POST /stock/replenish/batch`、`GET /stock/bill/page`。

**演示台词**："经理发现鲜牛奶只剩 3 瓶，低于安全库存 20。点补货、填 100、确认——库存立刻 103，POS 马上能卖。这一笔生成单据 IN20261020001，流水里能看到 3→103，操作人是张三。**库存每一次变化都有据可查。**"

### 7.3 模拟支付

`/pay/mock-callback` 只负责"制造回调"，**回调之后走真实幂等逻辑**。演示时故意连点两次"模拟成功"——库存只扣一次，这就是最好的幂等演示。

POS 加一个 demo 调试面板（仅 demo 环境）：支付结果（成功/失败/超时）、回调次数（1/2/5）、延迟（0/2/5s）。

`PayChannel` 接口不变，答辩时说："接真实微信只需新增一个实现类，业务代码零改动。"

### 7.4 演示数据

| 脚本 | 内容 |
|---|---|
| `demo-base.sql` | 1 门店、8 员工、3 角色、8 分类、60 SKU（含 8 个称重生鲜）、3 会员（正常/储值足/已过期）、2 活动、5 券 |
| `demo-orders.sql` | **300 笔跨 30 天历史订单**（报表要有曲线，否则全是 0） |
| `POST /demo/seed-orders`、`POST /demo/reset` | 仅 `@Profile("demo")`，一键造数据 / 一键复位 |

**演示前 3 分钟**：reset → 确认 2 个 SKU 库存不足 → 确认一会员已过期 → 确认有历史订单 → 打印测试页。

## 8. 质量门禁

### 8.1 一个接口算完成（7 条）

Swagger 可调通 · 有权限注解 · 参数校验走统一错误码 · 金额是 `long` 分 · 写操作有事务 · 关键路径有单测 · Postman 有请求且跑通。

### 8.2 一个页面算完成（6 条）

真实接口联调 · 加载/空/错误三态 · 无权限按钮不渲染 · 危险操作二次确认 · 两种分辨率不串版 · POS 可全键盘操作。

### 8.3 Code Review 10 条

事务边界 · 金额类型 · 身份是否从 Token 取 · 有无 N+1 · 创建类是否幂等 · 异常是否统一码 · 关键操作有无日志 · 状态变更是否过状态机 · SQL 是否走索引 · 有无残留调试代码。

### 8.4 W1 D5 必须完成的 5 项技术验证

| 验证 | 失败预案 |
|---|---|
| 扫码枪键盘输入 | 改手工输入 + 快捷键 |
| 58mm 小票打印 | 虚拟打印机 / PDF 预览 |
| 100 线程抢 1 件库存 | 降级为 Redis 原子扣减 |
| JWT 越权拦截 | 补 `dataScope` |
| 换机 `docker compose up` | 退化为本地安装脚本 |

### 8.5 AI 使用规则

| 适合 AI | 不适合 AI |
|---|---|
| CRUD、DTO/VO 转换、Mapper | 状态机、库存不变式、分摊算法 |
| 前端列表页/表单/弹窗 | 事务边界、并发控制、幂等 |
| 建表 SQL、单测骨架 | 权限拦截、越权防护 |
| 文档排版与改写 | 接口契约决策 |

**三条铁律**：AI 代码必须能逐行解释；契约不许 AI 定；公共件只允许一套（由 A 提供）。
**三个翻车点**：三套 `request.js`、Spring Boot 2.x 的 `javax.*`、演示时答不出"这段为什么这么写"。
