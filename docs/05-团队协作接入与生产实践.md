# 上半部分 · 组员怎么接进来

## 1. 先决定用哪种接入方式

仓库是**公开**的，所以组员**不加入也能克隆和跑**。区别只在能不能推代码：

| 方式 | 需要组长做什么 | 组员能做什么 | 适用 |
|---|---|---|---|
| **A. Collaborator（推荐）** | Settings → Collaborators 邀请 | 直接推分支、开 PR、改 Issue | 正式组员，5 人 |
| **B. Fork + PR** | 什么都不用做 | 只能往自己那份推，再发起 PR 回主库 | 临时帮忙的人、外校同学 |
| **C. 只读** | 什么都不用做 | clone、跑起来、看代码 | 老师、助教、旁听 |

**给 5 个组员用 A。** 理由：B 方式下组员之间看不到彼此的中间分支，`git pull` 也拉不到对方的进度，"每天推一次让别人看到"这条就废了。

> 公开库的一个副作用：**你写的每一行代码、每一条提交信息，老师都能看到，且永久留存。**
> 这对课程作业是加分项（能证明工作量），但也意味着提交信息里不能写"先随便糊一下"。

## 2. 组长现在要做的四件事

按顺序做完，再发通知。

### ① 加 Collaborator

```
仓库页 → Settings → Collaborators and teams → Add people
→ 输入组员的 GitHub 用户名或邮箱 → 选 "Write" 权限 → 发送邀请
```

组员要在自己的 GitHub 通知里或邮箱里点接受，**才算真的加进来**。

> 权限给 `Write` 不要给 `Admin`。`Admin` 能删仓库、能改分支保护、能把我设的规则全拆了。
> 六个人里只有你一个 Admin。

### ② 给 `main` 开分支保护

这是**整套协作的地基**。不设这个，`03` 文档里写的"没人能直接推 main"就只是一句口号。

```
Settings → Branches → Add branch protection rule
  Branch name pattern:  main
  ☑ Require a pull request before merging
      → Require approvals: 1
      → ☑ Dismiss stale pull request approvals when new commits are pushed
  ☑ Require status checks to pass before merging
      → 搜索并勾选：后端编译 / 前端构建 / 仓库卫生检查 / 编排文件校验
      → ☑ Require branches to be up to date before merging
  ☑ Require review from Code Owners
  ☑ Do not allow bypassing the above settings
  ☐ Allow force pushes          ← 一定不要勾
  ☐ Allow deletions             ← 一定不要勾
```

几处容易踩的细节：

- **状态检查列表是空的？** 因为 CI 还没跑过。先按第 3 节推一次，跑出绿色对勾再回来勾选。
- **"Require branches to be up to date"** 会让组员每次合并前都得先 rebase 到最新 main。严格但必要——否则两个人各改了一处，测试都过，合进去就崩。
- **"Do not allow bypassing"** 连你自己也绕不过去。这是好事：组长直推 main 是小组作业烂掉的第一大原因。

> 免费账号在**公开仓库**上也能用分支保护，不用升级付费。

### ③ 确认 Actions 已启用

```
Settings → Actions → General → Actions permissions
→ 选 "Allow all actions and related workflows"
```

**公开仓库的 Actions 分钟数不限量、不计量**。这是把仓库设成 public 而不是 private 的直接好处之一：CI 随便跑，不用担心额度。

### ④ 把 CODEOWNERS 里的用户名换成真的

`.github/CODEOWNERS` 现在所有路径都指向组长。组员账号收齐后，把注释里那张表填上，再按模块改。

> 不填也能用，但所有 PR 都会默认找组长 review。五个人同时开 PR 时你会成为瓶颈。

## 3. 组员那边的完整流程（可直接转发）

### 3.1 一次性配置

```bash
# ① 生成 SSH 密钥（已有就跳过）
ssh-keygen -t ed25519 -C "你的GitHub邮箱" -f ~/.ssh/id_ed25519_github
cat ~/.ssh/id_ed25519_github.pub
# 把输出的整段内容粘到 GitHub → Settings → SSH and GPG keys → New SSH key

# ② 国内 443 端口不通的话，在 ~/.ssh/config 里加这四行
#     （Windows 路径：C:\Users\<你>\.ssh\config）
# Host github.com
#   HostName ssh.github.com
#   Port 443
#   User git

# ③ 验证
ssh -T git@github.com
# 看到 "Hi <用户名>! You've successfully authenticated" 就成了

# ④ 设置署名（不设的话提交记录里显示的是乱码或别人的名字）
git config --global user.name  "你的真实姓名"
git config --global user.email "你的GitHub邮箱"
```

### 3.2 拉代码 + 跑起来

```bash
git clone git@github.com:zgong545-eng/supermarket-pos.git
cd supermarket-pos

cp .env.example .env          # 本地开发用默认值即可
docker compose --profile full up -d --build
```

首次构建约 3–6 分钟（要拉镜像、编后端、编前端）。起来之后：

| 入口 | 地址 | 账号 |
|---|---|---|
| 管理端 | http://localhost:8088/#/admin | `admin` / `admin123` |
| 收银端 | http://localhost:8088/#/pos | `cashier` / `cashier123` |
| 会员 H5 | http://localhost:8088/#/h5 | 任意手机号 + 验证码 `1234` |

**验收标准：三个端都能登录、管理端看板有数据、收银端能完整收一笔钱。**
做不到就别往下走，先解决环境问题——否则你会在一个坏掉的环境上写三天代码，最后发现全是环境问题。

> 只想写后端不想碰容器？`docker compose up -d mysql redis` 只起中间件，
> 后端在 IDEA 里跑 `PosApplication`，前端 `cd frontend && npm run dev`。见 `04-Docker架构与运行手册.md`。

### 3.3 日常循环

```bash
git checkout main && git pull --rebase     # 1. 每天开工先同步
git checkout -b feature/T-B12-stock-lock   # 2. 开分支，名字带任务号
# …… 写代码 ……
git add -A
git commit -m "feat(M03): 库存预占三态 lock/release/commit"
git push -u origin HEAD                    # 3. 下班前推，哪怕没写完
```

没写完也要推。推上去的是**你自己独占的分支**，不影响任何人。组长周五看分支列表就知道谁卡住了。

### 3.4 开 PR 合进 main

推完分支后，GitHub 页面会直接弹出一条黄色提示条 **"Compare & pull request"**，点它。

- 标题照抄提交信息格式：`feat(M03): 库存预占三态`
- 正文按模板逐项勾（模板已配好，会自动出现）
- 右边 Reviewers 会自动带出 CODEOWNERS 指定的人
- 等 CI 四项全绿 → 等 review 通过 → 点 **Squash and merge**

**用 Squash 不用 Merge commit**：五个人的分支合并历史如果都保留，`main` 的 `git log` 会变成一张蜘蛛网，答辩时没法用它证明进度。Squash 会把一个分支的所有提交压成一条，主干干净。

合并后：

```bash
git checkout main && git pull
git branch -d feature/T-B12-stock-lock     # 本地删
git push origin --delete feature/T-B12-stock-lock   # 远端删
```

## 4. 六个人同时干活，怎么不互相踩

### 4.1 谁碰哪块，写死在协作规则里

`docs/03` 第 5 节有"谁 Review 谁"的表，本质是**修改权归属**。重申三条最容易破的：

1. **`common/` 和 `config/` 只有 A 能改。** 这两个目录被 13 个模块依赖，任何人改一个方法签名，全组编译不过。别人要用新工具方法，找 A 加，不要自己动手。
2. **接口签名变化必须提前在群里说。** 你们现在前后端已经分离，`api.js` 里每个路径都对着一个 Controller 方法。改一个 `@RequestParam` 名字，前端就 400。
3. **`db/migration/` 下的 `V1__`、`V2__` 已经执行过，永久冻结。** 要加字段就新建 `V3__add_xxx.sql`。改已经跑过的脚本，Flyway 会校验 checksum 报错，而且别人库里已经是旧结构，你的改动对他无效——这是最难查的一类问题。

### 4.2 数据库迁移的正确姿势

```bash
# 加字段：新建文件，不动老的
# backend/src/main/resources/db/migration/V3__add_order_remark.sql

ALTER TABLE so_order ADD COLUMN remark VARCHAR(255) NULL COMMENT '订单备注' AFTER status;
```

三条硬规则：

- **只增不改。** 已存在的 `V*` 文件一旦被别人的库执行过，改它就是制造事故。
- **写可重复执行的语句。** 用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`（MySQL 8 不支持，改用先查 `information_schema`）或干脆加在末尾新增字段，避免"我本地跑过了他本地报错"。
- **改结构前先在群里喊一声。** 有人正在跑着 `mvn`，你改表他立刻挂。挑个大家都收工的时间点（比如晚上）推迁移。

### 4.3 冲突了怎么办

见 `docs/03` 第 7 节。这里只补一条实战建议：

**冲突集中在 `api.js`、`router.js`、`AdminLayout.vue` 这类"注册表"文件上。** 因为每个人都要往里加一行。解法不是抢着改，而是**提前把注册动作合并**：

- `api.js`：谁加接口，直接在群里发一行，让当天最后收工的人统一加。
- `router.js`：路由按端分组、组内按模块字母序，冲突了按字母序排就行，不用讨论。
- 菜单项：同理。

### 4.4 三个必须打的 tag

`docs/03` 第 8 节已经写了 `v0.4-checkout` / `v0.6-freeze` / `v1.0-demo`。补一句为什么：

答辩时评委问"这是最后一周赶出来的吗"，你打开 `github.com/.../tags` 和提交时间线，**比任何解释都有说服力**。反过来，如果所有代码都是同一天提交的，说什么都没用。

# 下半部分 · 真实生产环境该怎么做

## 5. 一张总表：我们有什么、生产要什么

| 维度 | 现在（课程版） | 生产标准做法 | 差距 |
|---|---|---|---|
| 分支 | `main` + `feature/*`，保护规则待配 | `main`（保护）+ `develop` + `release/*` + `hotfix/*` | 小 |
| 版本 | 三个手打 tag | 语义化版本 `v1.4.2` + CHANGELOG 自动生成 | 小 |
| CI | 新加的：编译 + 构建 + 卫生检查 | 加单测覆盖率门禁、静态扫描、依赖漏洞扫描 | 中 |
| CD | 手动 `docker compose up --build` | 镜像推仓库 → 自动部署 → 健康检查 → 失败自动回滚 | **大** |
| 密钥 | `.env` 文件放本机 | KMS / Vault / 云厂商密钥服务，容器只拿临时凭证 | **大** |
| 环境 | 一套，本机 | dev / staging / prod 至少三套，配置靠环境变量注入 | **大** |
| 数据库 | Flyway 自动迁移，无审批 | 迁移脚本走 PR 评审 + 备份 + 灰度执行 | 中 |
| 监控 | 日志 `docker logs` | 指标（Prometheus）+ 日志聚合（Loki/ELK）+ 告警（Alertmanager） | **大** |
| 多实例 | 单容器 | 后端多副本 + 网关负载均衡 + 共享 Redis | 中 |
| 回滚 | 重新 `up --build` | 镜像 tag 回滚（秒级）+ 数据库向前兼容迁移 | 中 |
| 审计 | 有 `sys_log` 表但没真用 | 全量操作审计 + 留存期策略 + 不可篡改 | 中 |
| 权限 | 4 个角色 33 个权限 | RBAC + 数据行级权限 + 最小权限 + 定期复核 | 小 |

**结论先说：差距最大的三块是「密钥管理」「环境隔离」「可观测性」，不是代码质量。**
课程作业通常在这三块上是空白，而这恰恰是生产环境最先出事的地方。

下面逐项展开。**每一项都会说清"为什么生产必须这样"，而不是列单词。**

## 6. 分支与版本：从"能协作"到"能发布"

### 6.1 生产的分支模型（GitHub Flow 的加强版）

```
main ──────●────────●─────────●────────●────→  永远等于线上运行的版本
            \      /          /        /
             ●────●          /        /         release/1.4（发版前稳定化，只修 bug）
                  \         /        /
feature/*           ●───●──●        /          日常开发
                                    /
hotfix/*                           ●           线上炸了，从 main 拉，修完同时合回 main 和 develop
```

关键差异：**`main` 在生产里是"已发布"的意思，不是"最新代码"。**

你们现在是 `main` = 最新代码。这个简化在课程作业里没问题（没有"线上"这回事），但要理解它的代价：**没有回滚锚点**。生产如果 `main` 一出问题，你分不清"哪个 commit 是好的"。

对应做法：

```bash
# 每次上线打一个 tag，tag 指向的 commit 就是线上跑的代码
git tag -a v1.4.2 -m "2026-11-20 上线"
git push origin v1.4.2

# 线上炸了，回滚
git checkout v1.4.1     # 或者直接部署 v1.4.1 的镜像
```

### 6.2 语义化版本怎么用

- `1.4.2` → 主版本.次版本.修订号
- 修订号 +1：只修 bug，不改行为（`fix`）
- 次版本 +1：加功能，向后兼容（`feat`）
- 主版本 +1：破坏性变更，接口不兼容（`BREAKING CHANGE`）

对课程作业的价值：报告书"维护"章节（10 分）可以直接写"本项目按语义化版本管理，v0.4→v0.6→v1.0 三次发布"。这比空谈"我们会做好版本管理"实在。

## 7. CI/CD：从"能编译"到"能部署"

### 7.1 现在已经有的

`.github/workflows/ci.yml` 四个 job：

| Job | 干什么 | 拦住什么问题 |
|---|---|---|
| 后端编译 | `mvn -DskipTests compile` | 有人提交了编译不过的代码 |
| 前端构建 | `npm ci && npm run build` | 依赖锁文件不同步、模板语法错 |
| 仓库卫生 | 查 `.env` / 构建产物 / 私钥 | 口令泄露（**公开仓库下这是致命的**） |
| 编排校验 | `docker compose config` | YAML 缩进错导致全组起不来 |

**这四个 job 是"及格线"，不是"优秀线"。** 生产还要加：

### 7.2 生产 CI 该加的四项

**① 单元测试 + 覆盖率门禁**

```yaml
- name: mvn verify
  run: mvn -B -ntp verify jacoco:report

- name: 覆盖率检查
  # 库存、支付、促销分摊这几个纯逻辑类必须 ≥80%
  # 不设门禁的覆盖率报表没人看
  run: mvn -B jacoco:check@check-coverage
```

对你们的实际意义：M03 库存预占、M07 支付幂等、M05 优惠分摊这三个是**纯函数/单表操作，最好写测试**，也最需要测试。答辩时"我们有 47 个单测，覆盖了尾差补齐的三种情况"是硬分。

**② 静态扫描**

```yaml
- name: SpotBugs
  run: mvn -B spotbugs:check
```

主要能抓到：`double` 算钱、空指针、资源未关闭。**`double` 算钱这一条在你们项目里是重点** —— 金额一律 `long` 分，但总有新人不小心写 `BigDecimal` 或 `double`。SpotBugs 能自动拦。

**③ 依赖漏洞扫描**

```yaml
- name: 依赖漏洞
  uses: aquasecurity/trivy-action@master
  with:
    scan-type: fs
    severity: CRITICAL,HIGH
    exit-code: '1'
```

**④ 镜像扫描 + SBOM**

打包成镜像后再扫一遍。生产要求能回答"这个镜像里有哪些组件、什么版本、有没有已知 CVE"。

### 7.3 CD：镜像怎么到线上去

课程作业是 `docker compose up --build` 就地构建。生产**绝对不在服务器上构建**——服务器只拉现成镜像。

```
CI 通过 → 构建镜像 → 推私有仓库（打 commit sha 标签）→ 部署平台拉取 → 滚动更新 → 健康检查 → 失败回滚
```

```yaml
# 关键：镜像 tag 用 commit sha，不用 latest
- name: 构建并推送
  run: |
    IMAGE=ghcr.io/zgong545-eng/supermarket-pos
    docker build -t $IMAGE:${{ github.sha }} -t $IMAGE:main .
    docker push $IMAGE:${{ github.sha }}
```

**为什么不能用 `latest`**：`latest` 是个指针，会变。出事时你想回滚到"上一个版本"，但 `latest` 已经被覆盖了，你根本不知道上一个版本是什么。用 commit sha，每个镜像都能精确对应一行代码，回滚就是换个 sha。

`ghcr.io`（GitHub Container Registry）对公开镜像是免费的。

## 8. 密钥、环境、可观测性：生产真正的分水岭

### 8.1 密钥管理

**现在**：`.env` 文件放本机，`docker compose` 读进去。`.env` 被 gitignore，`.env.example` 只有占位符。

**这个做法在课程作业里是对的**，因为：

- 没有真实用户数据；
- 演示环境就在自己机器上；
- 让组员能一条命令跑起来，比安全更重要。

**生产的做法**：

| 内容 | 生产该放哪 | 为什么 |
|---|---|---|
| 数据库口令 | 云厂商密钥服务 / Vault，应用启动时拉取 | 不进文件、不进镜像、不进环境变量 |
| JWT 签名密钥 | 同上，且**定期轮换** | 泄露等于任何人都能伪造任意用户 |
| 第三方 API Key | 同上 | 同上 |
| 支付渠道私钥 | HSM / KMS，绝不出硬件 | 最高等级 |

三条铁律：

1. **密钥绝不进镜像。** 镜像会被推到仓库、被拉下来、被缓存，一旦打进去就等于公开。
2. **密钥绝不进 Git 历史。** 改文件没用，必须**换密钥**。这是 `docs/03` 第 6 节第 4 条的原话，也是答辩可能被问的点。
3. **密钥要有轮换机制。** 一个从不更换的口令，等于一个迟早会泄露的口令。

> 具体到你们的项目：`application.yml` 里的 `pos.jwt.secret` 现在是硬编码的默认值。
> 上生产必须改成从环境变量读，且长度 ≥ 256 位。演示版可以留着，但**报告书里要写明这是演示配置**。

### 8.2 环境隔离

**现在**：一套环境。本机跑，数据是自己造的演示数据。

**生产**：至少三套。

| 环境 | 用途 | 数据 | 谁能碰 |
|---|---|---|---|
| dev | 日常开发 | 假数据 | 全员 |
| staging | 上线前验收，**配置与生产一致** | 脱敏后的生产数据副本 | 全员只读，部署由 CI 做 |
| prod | 真实用户 | 真实数据 | 只有运维，且操作留痕 |

**staging 存在的唯一理由**：让"上线"这件事在跟生产一样的环境里演一遍。没有 staging 的团队，上线就是赌博。

对应到代码：配置全靠环境变量注入，一份代码跑三处。

```yaml
# application.yml（提交进仓库，不含任何密钥）
spring:
  datasource:
    url: ${DB_URL:jdbc:mysql://localhost:3306/pos}
    username: ${DB_USER:pos}
    password: ${DB_PASSWORD}     # 不给默认值，缺了就直接启动失败
```

**注意 `DB_PASSWORD` 不给默认值。** 给默认值的后果是：忘配了也能启动，连到某个空库上，跑了一周才发现数据全在内存里。**启动失败比静默错误好一万倍。**

### 8.3 可观测性：三根支柱

**现在**：`docker logs pos-backend` 看日志，出问题靠猜。

**生产**：

| 支柱 | 工具 | 回答什么问题 |
|---|---|---|
| **指标 Metrics** | Prometheus + Grafana | 系统健康吗？QPS 多少？P99 延迟多少？错误率涨了吗？ |
| **日志 Logs** | Loki / ELK | 这个订单为什么失败？当时发生了什么？ |
| **链路 Tracing** | Jaeger / SkyWalking | 这请求走了哪些服务？慢在哪一段？ |

Spring Boot 3 接入几乎零成本：

```xml
<!-- 加两个 starter 就行 -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      probes:
        enabled: true        # 暴露 /actuator/health/liveness 和 /readiness
```

`/actuator/health/readiness` 这个端点在生产里是**必需品**：滚动更新时，新副本没准备好就不能接流量。没有它，你会把请求打到还在启动的实例上，用户看到一片 502。

**要监控什么**（不超过十项，多了没人看）：

1. 四个 9 目标：可用性、错误率、P99 延迟、吞吐
2. 数据库连接池使用率（满了就是雪崩前兆）
3. Redis 命中率
4. JVM 堆使用率与 GC 时间
5. 业务指标：每分钟成交笔数、支付成功率、库存预占超时数

> 第 5 项是关键。**技术指标能告诉你系统活着，业务指标才能告诉你系统有没有在干正确的事。**
> 支付成功率从 99% 掉到 60%，技术指标全绿，但生意已经没了。

### 8.4 多实例部署

你们的后端是 **JWT 无状态**，这是天然优势：

```
        ┌──────────┐
用户 →  │ 负载均衡  │ → 后端副本 × 3（无状态，随便加）
        └──────────┘ → MySQL（主从）/ Redis（共享）
```

**为什么能无状态**：登录凭证在 JWT 里，服务端不存 session。任何副本都能处理任何请求。
**唯一的坑**：`pos_hold`（挂单）、`pos_shift`（班次）这些是**存在数据库里**的状态，多副本没问题；但如果哪天有人把"当前购物车"放进 `HashMap` 缓存，多副本立刻串数据。**所有状态必须落到 MySQL 或 Redis，不能放 JVM 内存。**

### 8.5 回滚预案

生产事故的标准处置顺序：**先回滚，再定位。**

| 事故类型 | 回滚动作 | 耗时 |
|---|---|---|
| 代码 bug | 部署上一个版本的镜像 tag | 秒级 |
| 配置错误 | 回滚配置中心 | 秒级 |
| 数据库迁移有问题 | **最难，见下** | 分钟到小时 |

**数据库迁移是唯一不能快速回滚的东西。** 你 `DROP COLUMN` 了，回滚代码也回不来数据。

所以生产的迁移铁律是**向前兼容**，分三步走：

```
第 1 次上线：加新字段（可空），代码同时读写新旧字段
第 2 次上线：代码只读写新字段，旧字段留着不用
第 3 次上线：确认无问题后，才删旧字段
```

**永远不要在一次上线里同时改代码逻辑和删字段。** 那等于把"回滚"这条路堵死。

> 这条对你们的实际启发：`docs/03` 里"`V1__`、`V2__` 冻结"的规则，本质就是向前兼容思想的简化版。
> 报告书"维护"章节可以写这个——**它体现的是"知道生产怎么运维"，而不只是"知道怎么把功能写出来"。**

## 9. 如果这个项目要继续做下去：迁移路径

按投入产出排序，**前两步做完就已经比绝大多数课程作业专业了**。

| 顺序 | 做什么 | 投入 | 收益 |
|---|---|---|---|
| 1 | 开分支保护 + 要求 CI 全绿才能合 | 10 分钟 | 主干永远可用，答辩时能拿出真实的协作记录 |
| 2 | 给库存/支付/分摊补单测 + 覆盖率门禁 | 1 天 | 答辩硬分；也是唯一能防"改 A 坏 B"的手段 |
| 3 | 接入 Actuator + 一个 Grafana 看板 | 半天 | 演示时可以现场展示"系统运行状态" |
| 4 | CD 到一台真实服务器（哪怕是内网虚机） | 1 天 | "我们的代码能自动部署到线上"比任何话都有力 |
| 5 | 加 staging 环境 | 2 天 | 只有在真的多人协作时才值这个成本 |

**不建议做的**：

- 拆微服务。六个人、七周，拆完联调成本吃掉全部时间，架构答辩还会被问"为什么这个规模要拆"。
- 上 Kubernetes。单机 docker compose 足够演示，K8s 的复杂度换不来任何分数。
- 做完整分布式追踪。没有跨服务调用，追链路是自我感动。

**判断标准始终是同一个：这项投入能不能换成答辩分，或者能不能降低"最后一周全崩"的风险。** 两个都换不来的，不做。

## 10. 一页速查

**组员今天要做的**

```bash
ssh-keygen -t ed25519 -C "你的邮箱" -f ~/.ssh/id_ed25519_github
# 公钥上传到 GitHub → Settings → SSH and GPG keys
git config --global user.name "真实姓名" && git config --global user.email "GitHub邮箱"
git clone git@github.com:zgong545-eng/supermarket-pos.git && cd supermarket-pos
cp .env.example .env && docker compose --profile full up -d --build
# 打开 http://localhost:8088 三个端都登一遍
```

**每天要做的**

```bash
git pull --rebase
git checkout -b feature/T-XXnn-说明
# 干活
git commit -m "feat(M03): 说明" && git push -u origin HEAD
# 开 PR → 等 CI 绿 → 等 review → Squash merge
```

**绝不能做的**

1. 直推 `main`（保护规则会拦，别绕）
2. 改已执行过的 `V*__*.sql`
3. 提交 `.env` / 私钥 / `target/` / `node_modules/`
4. `git push -f` 别人拉过的分支
5. 自己改 `common/` 和 `config/`

**生产五句话**

1. `main` 等于线上，每次上线打 tag
2. 服务器只拉镜像，不在服务器上构建
3. 密钥不进 Git、不进镜像、要能轮换
4. 数据库迁移向前兼容，永不在一次上线里删字段
5. 出事先回滚，再定位
